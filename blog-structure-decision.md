# Пункт 10 ТЗ — структура статей: конфликт с сохранением SEO-позиций

## Суть конфликта

Главный приоритет проекта (сформулирован в самом начале работы) —
**сохранить все текущие URL**, чтобы не потерять органические позиции.

ТЗ пункт 10 предлагает перейти на структуру:
```
/blog/dostavka-vody-brovary/
/blog/voda-19-litrov/
/blog/voda-dlya-ofisa/
/blog/obratnyj-osmos/
/blog/ochistka-vody/
```

Текущие реальные URL статей выглядят иначе, например:
```
/43-chistaya-voda-izbavlennaya-ot-khlora.html
/3-znachenie-vody-v-zhizni-cheloveka.html
```

Это два взаимоисключающих требования одновременно — needs решение
пользователя, не молчаливое исполнение одного из двух.

## Вариант А — оставить текущие URL как есть (безопаснее для SEO)

Ничего не менять в путях статей. Организовать "категорию блога"
логически — через страницу-хаб `/voda-h2o-stati/` (она уже существует),
с человеко-понятными ссылками на статьи, но БЕЗ смены физических путей
файлов.

Плюсы: нулевой риск потери позиций.
Минусы: URL менее "красивые" и предсказуемые для новых статей.

## Вариант Б — перейти на /blog/ структуру, с полной защитой SEO

Если пользователь всё же хочет "красивые" URL:

1. Создать новые страницы по новым путям `/blog/slug/`
2. На КАЖДОМ старом URL оставить 301-redirect на новый:
   ```
   # Пример для .htaccess (если Apache) или конфига хостинга
   Redirect 301 /43-chistaya-voda-izbavlennaya-ot-khlora.html /blog/ochistka-vody/
   ```
   Для статического хостинга без сервера (чистый GitHub Pages без бэкенда)
   301-редиректы средствами HTML не работают "как надо" — придётся либо
   переходить на Netlify/Vercel/Cloudflare Pages с поддержкой `_redirects`,
   либо держать старые файлы физически на месте с
   `<meta http-equiv="refresh">` — это работает хуже для SEO, чем настоящий
   301, но лучше, чем 404.
3. Обновить `sitemap.xml` — указать новые URL, но старые пока не убирать
   из индекса резко.
4. Ожидать временную просадку позиций на 2-8 недель, пока Google
   переиндексирует редиректы и передаст вес новым URL.
5. Мониторить Google Search Console на предмет ошибок обхода после
   перехода.

Плюсы: более чистая, масштабируемая структура на будущее.
Минусы: реальный риск временной потери трафика, требует более сложной
инфраструктуры хостинга (redirects), больше работы.

## Рекомендация

Раз изначальный и неоднократно повторенный пользователем приоритет —
"не потерять позиции" — **вариант А безопаснее** и должен быть выбран
по умолчанию, если пользователь явно не подтвердит готовность на вариант Б
и связанные с ним риски.

**Не делай этот переход молча — уточни у пользователя перед началом
работы над структурой статей.**

## ✅ РЕШЕНИЕ ПРИНЯТО ПОЛЬЗОВАТЕЛЕМ

Выбран **Вариант А** — текущие URL статей остаются без изменений.
НЕ переходить на структуру `/blog/...`. Пункт 10 ТЗ в этой части
считать отменённым/переопределённым этим решением. Организовать
блог логически через существующую страницу-хаб `/voda-h2o-stati/`,
без смены путей файлов.
